### 第5—15分钟 确认内部接口

不是先讨论网页URL。先确认“B怎么请C跑测试，C怎么交成绩单”。

拟议调用：run_tests(run_id, task_id, workspace, test_profile, timeout_seconds, code_version, artifact_dir) -> ToolResult。

这是讨论用签名，不是仓库已有实现。工作目录、命令与产物目录均由控制程序管理，模型不能任意指定宿主机路径或Shell命令。

| 项目 | 必须当场说明 |
| --- | --- |
| run_id、task_id | B生成运行编号，C原样绑定；不同测试call_id不同 |
| workspace | 在哪一个受控任务副本执行；不能误测上轮已修好的副本 |
| test_profile | C维护的预登记测试方案，映射固定argv；不是模型随便写命令 |

| artifact_dir | stdout、stderr、JUnit和JSON放哪里；相对路径基准统一 |
| ToolResult | 字段、类型、状态枚举、缺失数据处理保持一致 |

## 7 C今天的具体工作与交付

### C1 先判断环境实际可用性

前一小时内先给初步结论：已有可用容器/VM、需要配置、当前不可用或未验证。看见Docker版本号只证明客户端存在；还需实际运行固定已知程序并说明环境位置。

隔离检查包括：测试能启动、原生测试只读、测试端无模型密钥、工作范围受限、网络/资源限制、超时后能清理。只展示密钥是否存在的布尔结果，不能打印密钥值。

若隔离未确认，可继续审阅过的固定代码、静态JUnit、模拟超时与受控fixture检查。这些属于工具联调，不能登记隔离通过，也不能自动执行模型生成或未经审阅代码。

### C2 最小runner只先做好一件事

给它一个受控任务副本和test_profile，它真实执行预登记测试，保存stdout/stderr/JUnit，输出与版本对应的ToolResult。

每次call_id使用独立产物路径，不能复用上一次JUnit。超时或启动失败可能没有JUnit，此时junit_path为null并写明原因，不能造XML补齐字段或读取旧报告。

至少返回：run_id、task_id、call_id、phase、tool、status、verification_status、failure_class、exit_code、counts、duration_ms、code_version、stdout_path、stderr_path、junit_path。

counts至少区分通过、失败、错误、跳过；预期执行数、收集数量及测试清单哈希的位置由B/C确认。无法获得的数据明确未知；不能把None或解析失败自动变成0。

沿用当前接口草案：工具status为ok/failed/timeout/blocked；验证结论为passed/failed/not_run/inconclusive。若需要新枚举，必须共同升级，不能C写error、B却只识别blocked。

完整通过至少要求：退出码正确、JUnit可解析、预期测试确实完成、没有失败/错误、不因跳过或缺测虚增成绩。C独立核对实际代码版本，不能只抄入参。

| 超时 | C展示带输出fixture的结果 | timeout、日志完整保留、不因类型处理再次崩溃；清理范围如实写 |
| B/C联调 | B读取C同一结果 | run_id、task_id、版本和产物对应，缺字段不瞎猜 |
| UI交付 | 分支、源码、命令 | 能定位原型源码，静态状态说明清楚 |
| 执行环境 | C检查记录 | 如实写可用/未验证/不可用；未验证不准勾通过 |
| 政策材料 | PR或diff | 测试、角色、复验、枚举和scope变更互相一致 |

遇到失败，只改为未通过并写责任人和下一步，不让B/C为了表格好看把计数手填正确。

当天可出现三种结论：

- 内部工具联调通过且隔离已验证：次日接固定真实模型流程。
- 内部工具联调通过但隔离待补：工具成果保留，A协调主机，模型候选自动执行暂不开放。
- runner或P1仍有阻塞：优先修执行器/适配，次日不扩大数据集和UI工作量。
