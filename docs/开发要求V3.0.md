## 二、总体开发原则

在整个开发过程中，必须遵循以下原则。

### 1. 充分复用现有代码

首先检查仓库的实际情况。对于已经实现且测试通过的功能，不要重复开发。对于已经实现但存在问题的功能，优先修复。对于完全缺失的功能，直接补充代码。不要无故推翻原有架构。

### 2. 保持现有 UI 和接口兼容

尽量保持现有 UI 结构、已确定的功能范围和已约定的接口。如果确实需要调整接口，请先解释原因、影响范围和兼容方案。

### 3. 使用适合小团队的技术

优先采用：
- Python
- FastAPI
- pytest
- Git
- GitHub
- 简单状态机
- 必要的大模型 API

不必为了实现多 Agent 而强制引入 LangGraph 等复杂框架。如果普通 Python 编排已经能够实现要求，就优先采用简单、稳定、容易维护的方式。

### 4. 保留现有三个 Agent

优先复用现有的修复员、检测员和调度员提示词。不要在不了解其功能的情况下重新设计全部提示词。如果确实需要修改，请说明修改原因，并保留原始版本。

### 5. 所有执行结果必须真实

禁止使用以下内容冒充实际运行：
- 虚构的 Agent 调用。
- 伪造的测试日志。
- 固定的测试成功结果。
- 未实际执行的补丁。
- 静态数据冒充动态调度。
- 没有执行的验收结果。

所有核心功能必须能够提供真实的运行证据。

### 6. 不增加已延后的复杂功能

不要擅自增加：
- 跨场景支持。
- 复杂可视化工作流编辑。
- 不必要的大规模框架。
- 与当前比赛核心目标无关的功能。

优先保证核心闭环真正可运行。

## 三、必须完成的核心功能

### 模块一：基础 Python 后端

实现一个能够真实运行的 Python 后端系统。至少包括：
1. 接收用户任务。
2. 验证任务参数。
3. 生成唯一任务编号。
4. 读取指定缺陷项目。
5. 管理任务运行状态。
6. 保存执行过程。
7. 记录异常信息。
8. 提供前后端通信 API。
9. 支持查询任务状态和执行结果。

必须能够从命令行或 API 启动，并提供真实运行结果。

### 模块二：真实 Agent 调用

将现有三个 Agent 提示词接入真实大模型 API。

**修复员 Agent**：负责根据代码、缺陷信息及测试结果分析问题，并生成候选修复补丁。

**检测员 Agent**：负责分析真实测试日志、识别失败类型、整理测试证据，并提出必要的补充验证建议。

**调度员 Agent**：负责根据实际测试证据和系统状态，建议下一步操作，例如：
- 继续修复。
- 重新定位问题。
- 补充测试证据。
- 进入独立验收。
- 暂停任务。
- 终止任务。

每个 Agent 必须具有明确的输入、输出和结构化数据格式。优先采用可验证的 JSON 数据结构。

API 密钥必须通过环境变量读取。禁止将 API 密钥直接写入代码或提交到 GitHub。

如果缺少模型密钥或相关权限，应准确报告阻碍，不得使用伪造调用冒充真实结果。

### 模块三：多 Agent 编排与协作

实现三个 Agent 之间的自动信息传递。基本流程为：

```text
用户提交缺陷任务
        ↓
后端读取代码与任务约束
        ↓
修复员 Agent 分析并生成补丁
        ↓
系统检查补丁合法性
        ↓
在受控工作副本中应用补丁
        ↓
执行真实 pytest 测试
        ↓
检测员 Agent 分析测试证据
        ↓
调度员 Agent 决定下一步策略
        ↓
系统执行调度决策
```

整个流程必须由 Python 后端自动编排。不允许依赖人工反复复制 Agent 输出。

### 模块四：真实代码修复与测试

支持读取指定 Python 缺陷案例。修复员生成补丁后，系统必须执行安全检查。至少包括：
1. 检查补丁格式。
2. 检查允许修改的文件路径。
3. 拒绝修改禁止路径。
4. 检查补丁是否能够正常应用。
5. 在受控工作副本中应用修改。
6. 使用 pytest 执行真实测试。
7. 保存测试退出码。
8. 保存标准输出和错误输出。
9. 保存执行耗时。
10. 保存补丁差异。

对于公开数据集或其他不可信代码，必须使用隔离执行环境，并设置超时、资源限制及必要的权限限制。禁止直接在宿主环境运行未经信任的代码。

如果安全执行环境尚未具备，应暂停相应测试并报告，而不是绕过安全限制。

### 模块五：测试证据驱动的动态调度

这是项目最重要的创新功能之一。

**必须让真实测试证据影响调度决策，而不是简单按照固定顺序调用 Agent。**

至少支持以下情况：

| 测试情况 | 系统处理方式 |
|---|---|
| 测试通过 | 进入独立验收 |
| 断言失败 | 分析原因，必要时重新修复 |
| 语法错误 | 返回修复阶段 |
| 环境异常 | 暂停并记录异常 |
| 修改违反路径限制 | 拒绝补丁 |
| 达到最大轮次 | 停止修复 |
| 独立验收失败 | 标记失败并保存证据 |

调度员 Agent 可以提供策略建议。但以下规则必须由 Python 程序强制执行：
- 最大修复轮次。
- 禁止修改路径。
- 执行超时限制。
- 任务暂停条件。
- 任务终止条件。
- 其他安全限制。

不能完全依赖大模型自行遵守这些规则。

### 模块六：自动修复闭环

实现以下完整流程：

```text
读取真实缺陷
      ↓
调用修复员
      ↓
生成候选补丁
      ↓
检查并应用补丁
      ↓
运行真实测试
      ↓
分析测试证据
      ↓
动态调度
      ↓
判断是否继续修复
      ↓
必要时进入下一轮
```

系统应能够在规定最大轮次内自动执行。每轮必须保存：
- Agent 输入与输出。
- 补丁差异。
- 测试日志。
- 测试结果。
- 调度决策。
- 调度理由。
- 执行时间。

### 模块七：独立验收

必须实现独立于开发测试的最终验收过程。在独立工作副本或隔离环境中，对最终补丁重新运行指定验收测试。

必须明确区分：**开发测试通过 ≠ 独立验收通过。**

未实际运行的验收只能标记为：**未运行。** 不能显示为通过。独立验收失败时，应记录失败证据。

### 模块八：知识库定义与知识集成

根据现有项目设计，实现必要的知识管理和集成能力。可以优先采用：
- 项目规则文档。
- 修复经验记录。
- 常见错误知识。
- 项目测试规范。
- 可检索的本地知识文件。

不必为了实现知识库强制引入复杂向量数据库。但必须保证知识内容可以被 Agent 在执行过程中真实读取或引用。不能只在 UI 中展示知识库名称，却没有实际使用。

### 模块九：运行证据与报告

系统必须能够保存并追溯完整运行过程。包括：
1. 任务编号。
2. 任务输入。
3. Agent 调用记录。
4. 补丁差异。
5. 测试日志。
6. 调度决策。
7. 修复轮次。
8. 独立验收结果。
9. 最终任务状态。
10. 必要的异常记录。

生成的报告必须与真实执行数据一致。无法确定的费用显示为“未知”。不得编造模型调用成本或测试指标。

### 模块十：前后端完整联通

将真实后端连接到现有 UI。至少实现：
- 创建修复任务。
- 配置任务约束。
- 启动任务。
- 查看任务运行状态。
- 查看 Agent 执行步骤。
- 查看测试证据。
- 查看调度决策。
- 查看独立验收结果。
- 下载运行报告。

前端必须展示真实后端状态。不得使用模拟动画或虚构结果冒充实际运行。

## 七、GitHub 版本管理、模块提交与安全回退机制

这是整个项目开发过程中必须执行的重要要求。

### 7.1 版本管理总体目标

**每完成一个完整的大模块，都必须保存一个可以追溯、检查和回退的独立版本。**

这样即使后续开发发生严重错误，也可以恢复到之前已经验证通过的版本。不得因为新模块开发失败而丢失之前已经完成的成果。

### 7.2 开发前检查 GitHub 仓库

开始修改代码前，必须检查：
1. 当前所在分支。
2. 最近的提交记录。
3. 未提交的本地修改。
4. 远程分支情况。
5. 现有版本标签。
6. 是否存在其他队员正在修改的文件。

不得擅自覆盖团队成员的代码。如当前仓库已有规范的分支管理方式，应优先遵循现有规范。

否则，建议创建独立开发分支：`codex-development`。

Codex 的开发工作优先在该分支或其功能分支中进行。

**未经明确授权，不允许直接修改或推送到 main 主分支。**

### 7.3 每完成一个大模块，保存一个新版本

每完成一个完整功能模块后，必须执行以下流程：

```text
完成模块开发
      ↓
运行相关测试
      ↓
检查测试结果
      ↓
检查代码修改范围
      ↓
创建 Git Commit
      ↓
测试通过并满足验收要求
      ↓
创建版本 Tag
      ↓
推送至授权的 GitHub 开发分支
      ↓
记录版本信息
      ↓
继续下一阶段
```

如果测试失败，应记录当前工作状态并继续排查。可以创建明确标记为未通过验证的开发提交，但不得将其标记为稳定版本。

### 7.4 版本命名规范

请采用清晰、容易理解的版本命名方式。参考规划如下：

| 版本 | 对应开发内容 |
|---|---|
| V1.0 | 基础后端与真实测试 |
| V1.1 | 修复员 Agent |
| V1.2 | 检测员与调度员 |
| V1.3 | 动态调度与自动修复闭环 |
| V1.4 | 独立验收、知识库及运行报告 |
| V1.5 | 前后端联通 |
| V1.6 | 系统集成与回归测试 |
| V2.0 | 完整参赛演示版本 |

以上只是参考规划。如果仓库中已有版本标签，应先检查，不能覆盖现有标签。可以根据实际开发情况调整版本编号。

### 7.5 分支管理机制

采用以下方式管理：

```text
GitHub 项目仓库
│
├── main
│   └── 稳定主分支
│
└── codex-development
    │
    ├── V1.0 基础后端
    │
    ├── V1.1 修复员 Agent
    │
    ├── V1.2 检测员与调度员
    │
    ├── V1.3 自动修复闭环
    │
    ├── V1.4 独立验收
    │
    ├── V1.5 前后端联通
    │
    ├── V1.6 系统测试
    │
    └── V2.0 完整演示版本
```

每一个稳定版本都必须对应明确的 Git Commit 和 Tag。

**不要求每一个版本都创建新分支，但必须保证每个版本都有独立、可恢复的提交节点。**

如果某个大型模块需要隔离开发，可以创建功能分支，例如：
- `feature/agent-repair`
- `feature/dynamic-scheduling`
- `feature/frontend-integration`

功能分支开发完成后，应进行测试和审查，再决定是否合并。不要自动合并到 main。

### 7.6 每次提交必须保存的信息

每完成一个大模块并提交 GitHub 后，必须向我汇报：

**版本编号：** 例如 V1.3

**模块名称：** 测试证据驱动动态调度

**实际完成内容：** 说明新增或修改的功能。

**修改文件：** 列出主要文件路径。

**测试状态：** 真实通过、失败或未执行。

**GitHub 分支：** 实际使用的分支。

**Commit ID：** 实际提交编号。

**Tag：** 实际创建的版本标签。

**远程推送状态：** 成功、失败或尚未执行。

**回退方式：** 说明如何恢复该版本。

**下一阶段：** 即将开发的模块。

不得编造 Commit ID、Tag 或 GitHub 推送结果。

### 7.7 安全回退机制

必须保证我可以恢复到之前已经测试通过的稳定版本。

例如：当前开发到 V1.5，但出现严重错误。我希望恢复到 V1.3。系统应能够根据 V1.3 对应的 Git Tag 或 Commit，恢复当时的代码状态。

但执行回退前，必须：
1. 检查当前未提交修改。
2. 检查回退对后续版本的影响。
3. 说明可能丢失或改变的内容。
4. 优先通过新分支恢复旧版本。
5. 在实际执行破坏性回退操作前取得我的明确确认。

禁止擅自使用危险命令覆盖或删除已有开发成果。

### 7.8 禁止破坏团队代码

未经我明确允许，不得：
- 强制推送覆盖远程提交。
- 删除稳定版本标签。
- 删除其他队员的开发分支。
- 重写团队提交历史。
- 将未经验证的代码直接合并到 main。
- 擅自丢弃未提交修改。
- 覆盖其他成员正在开发的文件。

如果发现代码冲突，应报告冲突位置，并优先采用不破坏现有成果的解决方式。

### 7.9 GitHub 推送权限

如果已经获得指定开发分支的推送权限，可以在每个模块通过测试后，按照本节规则自动提交并推送。

如果没有权限，应：
1. 保存本地 Git Commit。
2. 记录实际提交编号。
3. 保留当前代码。
4. 明确说明无法推送的原因。
5. 告诉我需要完成什么授权。

不得把本地提交说成已经上传 GitHub。

### 7.10 版本管理与自动开发结合

每个阶段按照以下顺序执行：

**开发 → 测试 → 修复 → 验证 → 版本提交 → 记录证据 → 自动继续。**

不能跳过验证直接宣布版本稳定。如果某个模块暂时无法通过测试，应明确记录阻碍，不得创建虚假的稳定版本。

**最终要求：整个项目每个关键开发阶段都有真实代码、真实测试记录、明确的 Git 提交和可恢复的版本标记。**
