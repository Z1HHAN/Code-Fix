## C的QuixBugs环境检查方法

完整仓库克隆到评测端独立目录，不能直接放进Agent可读项目目录。固定commit并记录git rev-parse HEAD。
在该目录、已准备的隔离环境中逐题执行：

```powershell
python -m pytest python_testcases/test_get_factors.py -v
python -m pytest --correct python_testcases/test_get_factors.py -v
```

另外两题分别替换为test_gcd.py、test_max_sublist_sum.py。
每条命令都由执行器设置超时，记录失败、跳过、未运行、退出码和耗时。
C已有首日基线和参考检查记录，见[已有成果与交接](已有成果与交接.md)；不必为了重复准备任务重新做一遍，但集成与独立验收仍须检查。
不向Agent工作区提供完整仓库：选定坏代码、开发测试、conftest.py、测试加载辅助和对应json数据等必要依赖由C审查后导出，不含正确实现与.git。
保留MIT许可声明。版本、来源、命令、结果记录在docs/成果登记与阶段结论.md的任务来源表中。

## 今天还要测平台自身

| 检查 | 怎么做 | 应该出现什么 |
| --- | --- | --- |
| 断言失败 | 使用实际失败开发用例 | Decision引用证据并回到定位，随后重修 |
| 环境异常 | C在专用副本故意设置不可用环境，标故障注入 | 暂停或infra_error，不让模型改业务逻辑凑通过 |
| 语法错误 | C用明确标注的无效候选检查流程 | 局部重修，不能宣布通过 |
| 上限停止 | 配置最大1轮，注入持续失败 | 1轮后停，无第2次修复请求、无遗留任务 |
| 越权修改 | 候选试图改测试或禁止路径 | 程序拒绝，代码未被改动 |
| 证据失效 | 某版本通过后再改代码 | 旧证据不能代表新版本，须重测 |
| 知识接入 | 使用knowledge/demo_project/的3条查询 | 命中来源实际进入角色输入并保存引用 |
| 暂停追加约束 | 步骤边界暂停，禁止原先允许路径 | 后续旧候选重新校验并被拒绝 |
| 独立验收 | 干净起点应用输出补丁，C运行保留测试 | 结果单独记录，细节不回流修复循环 |
| 他人复跑 | A按README在主执行机操作 | 无需B临时补步骤；问题如实记录 |

故障注入属于平台检查，不是公开任务修复成绩。一次注入用例不能证明实际恢复率提高。

## 怎样升级 不把旧任务直接修成好代码

- A配置和说明、B执行程序、C执行与验收各走任务分支，使用PR对齐。
- B改程序后，先跑平台检查，再用闰年新副本回归；不要在上次已修好的副本上假装从零修复。
- 闰年可用已知补丁做纯工具回归，必须标工具检查；要声称模型修复则必须有真实模型调用。
- 每次记录平台commit、配置版本、任务起点、补丁后版本、模型和预算；升级后继续相同任务便于比较。
- C审查和A验收后，B在合并后的准确提交打v0.2标签；未过项保留在阶段结论，不提前打完成标记。
- 后续v0.3再增加多文件任务与更完整交互；更后面冻结任务、模型和预算，比较单Agent/固定多Agent/动态流程。
