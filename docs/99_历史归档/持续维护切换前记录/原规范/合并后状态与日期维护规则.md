# 合并后状态与日期维护规则

适用所有A/B/C和Codex交付。当前唯一状态来源是[当前开发任务台账](../../../2026-11-03_项目持续维护/当前开发任务台账.md)，当前执行优先级见[当前开发计划](../../../2026-11-03_项目持续维护/当前开发计划.md)。本规则是每次交付必须执行的人工检查，不冒称已有自动同步程序。

## 每次提交、复核和合并的闭环

1. 拉取main后先记录实际基线commit与工作区状态；B/C在各自开发分支修改，不覆盖他人未提交内容。
2. 对照稳定任务ID记录本次完成部分、实现证据、实际测试命令/结果/产物；实现、开发测试和独立验收三列分别核对。旧commit的通过不能直接签新功能版本。
3. 已有可靠证据完成的部分从当前待办索引移入已完成索引，状态只在唯一台账维护；不重复立项、不凭代码存在就勾测试通过。
4. 未完成部分沿用原ID，写清阻塞/责任人/下一步并在当前计划调整优先级；不复制30号、1号、2号、3号的任务表形成多个当前计划。部分完成写范围，不能整项冒称通过。
5. 更新本轮docs/deliveries与daily记录、CHANGELOG、README入口/限制、相关当前规范和素材索引；文件改位置必须附映射、修好引用并跑受影响检查。
6. 审核通过后正常合并main，核对远端SHA；A登记主线合入状态。开发分支提交、主线合入、B/C本人签收、稳定版本是四件事，不能互相代替。

## 日期与版本如何处理

- YYYY-MM-DD是记录实际发生日，永远不为了“最新”将旧测试、旧包、历史目录改为今天日期。进入新一天时新增当日日志，不覆盖旧记录。
- 无日期的当前开发任务台账/当前开发计划一直维护同一文件，更新“最近核对日期”和实际证据；不会每天新建一份权威计划。
- 历史计划仍有效的义务已关联到任务ID，原文件归档并保留来源、真实日期、版本、证据。失效目标标明被哪个当前文档替代。
- V3.0是项目需求，0.2可能是工具接口/候选配置，1.0.0是runtime配置格式；组件版本须核实现，不批量替换版本号。
- GitHub列表的“备注/几小时前/几天前”显示文件最后一次提交，不能手工刷新成今天或据此判功能落后。通过有实质内容的提交更新；当前状态看台账和README核对日期，历史提交信息保留。

## 文件放置规则与边界

当前文档按00—09主题目录；历史日期/交付按99_历史归档；daily/deliveries保留协作固定入口；实际机器证据进evidence（本机临时与解释器在ignored runs）。正式源码/测试/夹具按当前包结构固定，不按日期搬家。C历史原交付已经归档，当前c_runner/c_tests/c_fixtures有运行路径依赖，见[C组件说明](../../../2026-11-03_项目持续维护/C测试组件与历史证据状态.md)。

未获得真实模型/费用/隔离条件时，状态写未运行或受环境阻塞；模拟结果标模拟。文档登记不能夹带未授权功能开发，仍按AGENTS由A先确认新增功能范围。
