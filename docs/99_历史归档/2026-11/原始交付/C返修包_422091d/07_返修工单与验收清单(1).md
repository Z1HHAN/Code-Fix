## 2. 建议的返修批次

**批次 1（证据可信，1 天）**：RF-01、RF-02、RF-04、RF-05、RF-06
- 全部低风险、可离线验证；
- 完成后在本机跑 `pytest tests` + PoC 全绿。

**批次 2（门槛与决策，1 天）**：RF-03、RF-07
- 会改变"25 项门槛"的口径，需要 A 先确认"旧通过记录作废、重跑"；
- 保留改前失败、改后通过两份输出。

**批次 3（流程，0.5 天）**：RF-11、RF-12、RF-14
- 入口规则变化，需同步更新 README/台账。

**批次 4（环境相关，1–2 天）**：RF-08、RF-09、RF-10、RF-13
- 必须在有 Docker / 双账号 / 长时测试的机器上做；
- 结果单独登记，不与离线结果混记。

## 5. 返修完成后的整体验收（C 视角）

必须同时满足，才可从"不签收"转为"可提交"：

1. 干净树 + 明确 commit 的完整入口一次通过（exit 0），且报告首行无 dirty 标注；
2. `git_status` 为空、`UU/AD` 为 0；
3. 证据包 `sha256.json` 自校验通过（含恢复的 27 个文件）；
4. 7 个 PoC 全部转绿（作为回归用例保留在 `tests/` 或 `c_tests/`）；
5. CODE-07 重写后 25/25，且 C 能复现"旧代码红、新代码绿"的两份输出；
6. 平台 362+/Node 23+/控制 12/12 不回归；
7. 真实 Docker 与真实模型的边界仍单独标注，不混入离线结论。
