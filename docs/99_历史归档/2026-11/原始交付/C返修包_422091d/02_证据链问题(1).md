# 证据链问题（02）

> 这一份是给 A 看的：**"最近一次完整 C 入口通过"这句话目前不成立**。不是测试套件坏了，而是通过结论绑定在错误的证据上。

## E-01 最近一次"完整入口"不在当前 commit，也不是干净树

**证据**：`evidence/integration-docker-loop/C-acceptance-20261106-014017-b626a073/summary.json`

| 字段 | 值 | 问题 |
|---|---|---|
| `repository` | `C:\Users\lenovo\Documents\ChatGPT\Code Fix` | B 机路径，不是本仓库 |
| `python` | `...\runs\v3-venv\Scripts\python.exe`（3.14.6） | B 机私有环境 |
| `source_identity.git_commit` | `69891c9...` | 当前 HEAD 是 `422091d` |
| `source_identity.git_status` | 共 **984 行** | 工作树极脏 |
| 其中 `UU` | **6 条**：`.gitattributes`、`app/account_budget.py`、`app/docker_runner.py`、`app/split_runner.py`、`docker/candidate_rpc.py`、`docs/.../持续交付与变更记录.md` | 处于未合并（合并冲突）状态 |
| 其中 `AD` | 18 条 | 已 add 后又删除 |
| `git_identity_verified` | `true` | 只表示 `rev-parse` 成功，**不表示工作树等于该提交** |
| `source_unchanged_during_checks` | `true` | 只表示运行前后一致，**不表示干净** |

**结论**：`git_commit=69891c9` 只能当**归档声明**。被测字节实际是"合并中、冲突已手工解决但未 `git add` 的工作树"，用 commit 号无法复现同一工作树。

**影响**：
- 不能用该 run 证明"commit 69891c9 通过"；
- 更不能用它证明"当前 HEAD 422091d 通过"；
- 评审/比赛提交若引用该 run，会被质疑证据与代码不对应。

**整改**：
1. 在干净工作树（`git status --porcelain` 为空）上，用明确 commit 重跑完整入口；
2. 若必须接受 dirty，入口需显式记录 `--allow-dirty` 并在报告首行标注"dirty 通过，不等于 commit 通过"；
3. `git_status` 中出现 `UU/AD` 时直接判环境错误，不产出 `passed_offline_scope`。

## E-02 归档证据包在当前工作树缺 27 个文件，无法自校验

**证据**：`git status --porcelain` 有 27 个 `D`（删除）条目，全部位于
`evidence/integration-docker-loop/C-acceptance-20261106-014017-b626a073/c_controls/.../work/...`。

- HEAD 中这些文件仍在（可 `git checkout -- <path>` 恢复）；
- 当前目录下 `sha256.json` 仍列出它们，逐个重算会失败；
- 若此时原地跑完整入口，`preserve_work` 与哈希核对会得到不完整结果。

**影响**：证据包不能独立自检，"已通过"无法被第三方复核。

**整改**：
1. 恢复 27 个文件（或从 HEAD 重新导出该证据目录）；
2. 重算 `sha256.json`；
3. 在 07 的 RF-02 工单里记录恢复前后的文件数。

## E-03 源码快照哈希对换行敏感，跨机不可比

**证据**：归档 `source-before.json` 与本机副本比对，116/398 个文件哈希不同，但**全部可由 CRLF/LF 解释**。

**影响**：
- 同一内容在不同换行设置的机器上会得到不同 `source_snapshot_sha256`；
- 跨机复核容易被误判为"源码被改"，或反过来掩盖真实改动（如果只比较哈希总数）。

**整改**：`scripts/c_acceptance.py` 的 `snapshot()` 在哈希前统一换行（`read_bytes().replace(b'\r\n', b'\n')`），并在 `report.md` 注明"哈希已归一化"。

## E-04 工作树与分支状态（记录，不算缺陷）

- 分支相对其远端 `origin/codex/b-real-docker-5-items-20261105` ahead 5；
- 但 `origin/main` 已包含 HEAD（`merge-base --is-ancestor HEAD origin/main` 为真），**"已合入 main 并推送"成立**；
- 27 个删除文件使 `git status` 非空，这会让任何"以工作树为准"的入口产生脏状态记录。

## 对 A 的建议顺序

1. 先处理 E-02（恢复证据文件，成本最低）；
2. 再处理 E-01（干净树 + HEAD 重跑完整入口，这是签收前提）；
3. E-03 随下一次入口改动一起做，避免重复跑；
4. 全部完成后，才具备讨论"是否签收当前实现"的证据基础。
