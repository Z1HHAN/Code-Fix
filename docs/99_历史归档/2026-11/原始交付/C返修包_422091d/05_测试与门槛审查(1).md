# 测试与门槛审查（05）

> 针对"25 项返修门槛 + C 执行器 + 入口脚本"的审查。核心结论：**门槛体系挡住了误判，但挡不住伪造；清单可收缩，脏树可通过。**

## G-01 CODE-01 的三个变体是装饰性的（P1）

**代码**：`acceptance_tests/test_repair_gates.py:105-128`

- `fake_execute` 返回的 dict **不含 `artifact_channel`**；
- `docker_runner.py:241-242` 因此必然判 `evidence_channel_tampered`；
- 三条参数化（`legacy_single_report` / `legacy_report_with_end` / `versioned_report_with_end`）构造的 stdout 载荷**从未被解析**，全部命中同一条分支；
- 归档 `work.zip` 中三个变体的 `result.json` 字节相同（`b3915c3226de`，724B），可作旁证。

**判断**：生产代码"只认 `docker-cp` 通道"本身是正确的；但这个门槛只证明了"没有通道标记就被拒"，没有证明"三种伪造格式都被识别"。

**建议**：
1. 合并为一个用例，明确断言回收原因（channel 缺失）；
2. 另加 Split 路径的"可信容器产证据 + 候选 RPC"用例（当前 25 项门槛**零覆盖 Split**）；
3. 若要测"伪造格式"，应让 `_execute` 返回 `artifact_channel='docker-cp'` 并写入伪造的 junit/structured，断言 `parse_evidence` 拒绝——但需先明确这是**期望拒绝**还是**已知风险**（见 R-02）。

## G-02 25 项门槛清单可收缩（P1）

**证据**：
- `acceptance_tests/case_map.json` 的 `required_testcase_count: 25` **没有任何代码读取**；
- `scripts/c_acceptance.py:265-271` 的 `assess()` 只按名字集合、数量、skipped 比对；
- `acceptance_tests/*` 与 `case_map.json` 本身没有外部哈希锚点。

**后果**：把某个门槛函数体改成 `assert True`（保留函数名）仍会通过；改 `case_map.json` 删一个名字也会通过（名字集合跟着变）。

**建议**：
1. `assess` 读取并校验 `required_testcase_count`；
2. 对 `acceptance_tests/*.py`、`case_map.json`、`configs/decision_rules.json` 计算哈希，写入 `summary.json` 并在复验时比对；
3. 在 C 报告里附"门槛文件哈希"一栏。

## G-03 platform / Node 阶段没有最小用例数（P2）

- `c_acceptance` 只检查"全绿"，不检查收集数/文件数；
- 删掉 `tests/test_x.py` 整个文件，剩余全绿也会 `passed_offline_scope`；
- Node 阶段同理（23 个用例没有名单）。

**建议**：为两个阶段各加最小收集数（platform ≥ 350、node ≥ 20，按当前基线留余量），并在报告里记录实际数。

## G-04 入口不 gate 脏树（P2）

**证据**：`c_acceptance` 只把 `git_status` 写进 `source_identity`，不因 dirty 判失败。

**后果**：这正是 E-01 的机制性原因——脏树也能拿到 `passed_offline_scope`。

**建议**：默认要求 `git status --porcelain` 为空；提供 `--allow-dirty` 显式开关，并在 `report.md` 首行标注"dirty 通过"。

## G-05 `parse_evidence` 只做一致性，不做真实性（P1，设计使然）

**证据**：`c_runner/runner.py:148-150` 自述；`:206-275` 只交叉校验 JUnit/structured/exit_code；`:436-453` 只检查文件存在与可解析，`integrity` 只重算 `work/workspace` 哈希，**不检查证据由谁写、何时写、是否被改**。

**后果**：恶意候选（或任何能写 `call_dir` 的代码）可伪造出 `passed`。风险取决于执行通道：
- 宿主 reviewed-fixture 形态：需先攻破注册表或 fixture 字节；
- 单容器 Docker 形态：`/out` 可写（见 R-02），现实攻击面；
- Split 形态：设计上更稳，但无门槛覆盖。

**建议**：
1. 在文档中明确"证据可信度 = 执行通道可信度"，不要用"parse_evidence 校验通过"暗示真实性；
2. 单容器路径补恶意变体；
3. 长期：证据由宿主进程写（容器只输出结果），或对证据加时间戳/一次性随机数绑定。

## G-07 进程树清理未被真正验证（P2）

**证据**：
- `c_runner/runner.py` 只做 `taskkill /T /F`；
- 没有 Job Object / 进程组回收；
- `cleanup.parent_reaped` / `pipes_drained` 的语义容易被读成"已清干净"；
- `full_process_tree_verified` 恒 `False`，且没有任何门槛检查它；
- 超时用例是**进程内 `time.sleep(30)`**，`taskkill /T` 从未被真正触发。

**后果**：Windows 上孙进程可能成为孤儿；"清理通过"是未经验证的声明。

**建议**：
1. 超时用例改为真实子进程（`python -c "import time; time.sleep(30)"`），断言进程树消失；
2. 引入 Job Object（带 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`）；
3. 若短期不做，在报告里把 `cleanup_passed` 明确标注为"仅 taskkill 成功"，不要让读者以为是树级回收。

## G-08 门槛与产品代码的"自证循环"（记录）

- 门槛测试用替身执行器，产品代码用真实执行器；两者之间没有"同一份恶意样本"的交叉验证；
- 归档证据显示 12 项控制全部 `passed`，但其中 `stale_version` / `modified_tests` 的拒绝发生在 `task.verify` 层，不涉及 Docker；
- 建议在 `docs/` 里明确每项控制覆盖的**层**（verify / runner / decision），避免读者高估覆盖。
