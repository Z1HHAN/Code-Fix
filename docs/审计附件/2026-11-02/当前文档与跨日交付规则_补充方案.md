## 3. 日期如何结转，怎样避免每天改路径

计划中的权威文件只有一份`docs/04_开发与任务管理/当前开发任务台账.md`；需求、UI、运行与测试规范也用稳定主题命名。执行日记录是台账的当日变化与交付来源，不再独立维护另一套总状态。

以11月3日为执行安排时：

1. 读取10月30日、11月1日、11月2日记录，对照当前代码和原测试，区分已完成、部分完成、未运行和阻塞。
2. 同一事项沿用统一任务ID及旧ID别名，不另起“3号同名任务”。更新下一步执行日和负责人，保留原计划日、来源、已完成部分及证据。
3. 已完成的从待办视图退出；仅代码完成、测试未跑的，保留“已实现/未运行”。过去通过的测试只支持相应代码，变更后需要重新验证受影响部分。
4. 新日期只新增当天实际计划/执行记录；11月3日尚未执行的测试不填通过、run_id或签收。
5. 当天遇到的新问题登记为下一步，不把原失败证据改成成功。日终未完继续结转同一ID，历史快照保持原义。

| 日期例子 | 历史事实 | 结转后的当前任务表述 |
| --- | --- | --- |
| 10月30日历史交付 | 原有结果、commit和日期保持不变 | 已完成部分进入完成视图；后续集成验收单列待办 |
| 11月1日至2日接口/环境任务 | 有实现与未签收项分别记录 | 已实现组件不重做；仍缺的目标机验证安排到下一执行日 |
| 11月3日执行安排 | 这是计划示例，不是已发生结果 | B执行补充、C复核，实际运行后才填写新证据 |

`C_Day1_20261030/`记录C首日历史交付，不是需要每天刷新日期的当前源码目录。其manifest、校验器与引用依赖固定文件名/路径，反复更名既可能破坏运行，也会把旧证据误写成新日期。它保留原位，由当前“测试与独立验收规范”和历史索引链接；未来的新运行按实际日期和run_id新增证据。

## 4. B/C每次拉取、交付、A复核的检查点

复用[现有分支提交规范](../../分支提交与版本记录规范.md)、[B/C交付模板](../../templates/BC分支交付记录模板.md)和[PR模板](../../../.github/pull_request_template.md)。它们已有手工流程，本补充拟明确与唯一台账的衔接；本轮未修改模板或AGENTS.md，不声称已有CI拦截。

| 时点 | 责任人 | 必须记录或核对的内容 |
| --- | --- | --- |
| 开始工作、拉取前 | B/C | `git status --short`；保全未提交变更，不reset清空；已有共享分支不强推、不重写 |
| 拉取后、开始修改前 | B/C | 当前分支、实际拉取时间、main基线SHA、统一任务ID与授权范围；新任务从最新main派生`codex/`分支 |
| 实现/复跑时 | B | 本人新增的行为、涉及文件、运行入口、相同范围的允许测试和原始结果；环境限制、模拟结果单独标明 |
| 针对B提交复核 | C | 明确B被测commit、测试版本、机器/隔离资格、原样命令、退出码、通过/失败/跳过、run_id和证据；代码变动后不沿用旧签收 |
| 每次交付可复核分支 | B/C | 提交`docs/deliveries/YYYY-MM-DD-B或C-主题.md`，附基线/被测commit、实现/测试/独立验收状态、遗留、A更新建议和PPT/demo材料 |
| 推送前 | B/C | diff中无密钥/缓存/无关改名/原始证据改写；文档与运行入口一致，改过的当前链接可用；正常推自己的分支，不覆盖main |
| 复核与合并 | A | 核对commit、证据可访问性及结论范围；缺记录不记为已复核；有实际合入后才登记主线变化 |
| 合入后的同一轮状态登记 | A | 更新唯一台账、功能状态、当前交接、CHANGELOG、素材索引，以及本次确有影响的需求/UI/运行/验收规范；列出无需更新的项目 |

交付记录必须具体写“改了什么、怎样运行、实际测了什么、还缺什么、A改哪些状态”。只写“已完成”“测试通过”或只放本机绝对路径不满足交付要求。先提交代码、再记录已经存在的被测commit，避免要求提交正文引用自身SHA。

“每次交付”指每次交给另一成员复核的分支成果；普通临时本地commit不要求重复写整份报告。同一天多次交付用不同主题或后缀，不覆盖旧记录。新增结论应明确它支持哪个提交；是否需要再次复跑取决于代码/测试/环境的实际变化。

## 5. 文档、脚本与证据放在哪里

| 材料 | 拟采用的位置与命名 | 当前约束 |
| --- | --- | --- |
| 当前权威需求/架构/台账/UI/测试规范 | 审计主方案的`docs/00_项目导航`至`09_配置与规范`；稳定中文主题名 | 第二阶段获批后建立；原入口在切换前仍有效 |
| B/C交付记录 | 已有`docs/deliveries/YYYY-MM-DD-B或C-主题.md` | 优先复用，不为中文目录统一擅自改GitHub模板依赖 |
| 日期执行记录 | 已有`docs/daily/YYYY-MM-DD.md` | 保持既有目录约定，正文说明主题；历史不重命名成当天 |
| 开发变更与PPT/demo素材 | 根`CHANGELOG.md`、已有`docs/版本与演示素材索引.md` | 按真实交付/合并更新；标现场、历史回放或模拟 |
| 可交付的运行证据 | 既有`evidence/`约定，按日期/主题/run_id组织 | 原始字节冻结；大文件走可访问存储，索引记录SHA256 |
| 历史普通文档 | `docs/99_历史归档/`及来源映射 | 获批、引用问题解决后再迁；存在冻结/路径约束的只做索引归档 |
| 源码、runner、fixtures、测试和环境 | 原功能目录 | 不属于本轮文档治理的搬迁或改名范围 |

目录规范允许固定入口与依赖路径例外，例外写清依据；不用重新移动运行组件来追求所有文件外观一致。根README和文档索引应直达当前规范，旧日资料只作为来源与历史入口出现。

## 6. 如何验收“同步了”，而不是只改了名字

- 每项旧义务能追到统一任务或明确保留理由，已完成成果不重复进入待开发；未核实的仍待确认。
- 台账中实现、测试、独立验收分列；当前结论有commit、证据、核对日期，历史测试不会冒充新提交成绩。
- 当前文档改用团队可访问链接；个人本机证据明确本机留存，不能写成已上传。
- B/C记录包含基线、实际被测代码、完整验证结果、A需更新的具体文件和素材；A复核记录与分支实际合入状态一致。
- 新规范和索引可达，旧入口兼容，业务/测试/配置/V3原文/冻结证据无改动；迁移均有映射和回滚提交。

这里的“随进度更新”是交付与合并时的固定检查，不是已实现的后台自动同步器。自动检查交付记录、链接或台账的CI属于可选后续工程，需要单独确认实现范围。本轮只补充可审批方案，不执行文件搬移、旧文件重写或功能开发。
