## 二 平台功能逐项核实

| 功能 | 当前事实 | 论文和PPT可使用的表述 |
| --- | --- | --- |
| 四个独立Agent | 修复员、检测员、模型调度员、定位员分别有实例ID、合同、输入输出权限与交接记录，可共用同一个基础模型 | 四角色独立合同与上下文协作，不等同四种模型或四个独立进程 |
| 证据驱动调度 | 语法、断言、运行、环境、权限及预算证据进入规则裁决；模型调度员提供建议 | 规则约束下的证据驱动条件调度，不宣称学习式调度或DAG优化 |
| 定位前置校验 | 定位必须同时接收当前检测输出和程序批准的分发指令，并匹配候选及证据 | 缺依赖或版本不匹配时，在调用模型前阻断 |
| 有界Self Loop | 候选真实测试后回检测；可修复失败按证据定位或重修；通过后最终复验 | 有界反馈闭环，成功提前停止，不是每题固定调用四角色 |
| 最终验收 | 干净副本执行同套冻结原生测试，最终结果不回流本轮Agent | 原生测试范围内验收，不能扩大为形式化正确性或隐藏测试通过 |
| 人工兜底 | 非成功任务生成handoff.json，记录原因、版本、证据、消耗和pending_human | 自动结束并生成待人工复核材料；尚不等于已有人员接手 |
| 人工处理系统 | 本批移交包accepted_by均为空；未核实到完整接单、分派、签收API和任务工作流 | 人工接单与处理闭环为待补齐能力，不写已完成人机接力闭环 |
| 实验对照模块 | 现有双组并排、逐题结果、请求、费用、耗时、原件入口及导出 | 可查看配对事实；人工移交率本次由原件另行统计，现界面不是完整统计工作台 |
| 提交自有样本 | 当前任务入口只选已登记题目，尚无一般用户上传源码和测试的已验收通路 | 本轮只提出受限Python样本接入方案，不放入已实现列表 |
| 网络与费用 | 明确未发送可有限重连并释放预留；符合条件的人民币未知费用按原上限预留继续 | 保守预算占用与实际扣费分别展示，尚未接通服务商账单查询API |

### 5.1 整体指标对比表

下表只使用原始同题配对的40条单Agent和40条多Agent运行，不混入恢复批次。每个均值都包含失败、暂停等非成功任务，分母为40。

| 模型请求总数 | 49 | 98 |
| 平均请求次数 每题 | 1.225 | 2.450 |

| 估算费用总计 CNY | 0.147057 | 未知 已知小计 0.286201 另预留 0.084076 |


统计定义应紧接表格：

- 修复成功率为干净最终复验通过题数除以40。
- 平均模型调用为已记录的实际发起模型请求总数除以40。它与角色尝试数、工具调用数分开，失败请求不能删掉。
- 平均耗时为每任务started至finished时长的总和除以40，含隔离、网络等待和工具测试。整批墙钟时间另含人工等待，不应用作模型推理时延。
- 人工移交包生成比例为有handoff.json的任务数除以40。本批均为pending_human，accepted_by为空，不能把5%和7.5%命名成人工实际介入比例。
- 缺少usage的请求不填0 Token；保留金额未知和预留上限。服务商用量缺失与人工核销金额为0是不同事实。

可直接使用的分析文字：在相同模型、冻结测试和每题资源上限下，单Agent组通过38/40，多Agent组通过37/40。多Agent平均请求次数较多，平均任务耗时也更高。两条多Agent网络暂停影响了整体结果；单次采样及任务规模有限，因此本实验不能证明多Agent整体优越，也不能把差异全部归因于调度策略。

两组都通过36题；仅单Agent通过2题，即flatten和shunting_yard，对应多Agent网络暂停；仅多Agent通过1题，即subsequences；两组都未通过1题，即next_palindrome。subsequences可作为单题差异，但没有重复运行和等实际调用对照，不能据此声称动态路由产生因果增益。

人工数据原件见 `../../evidence/recovery/113/materials/paired-metrics.json`。已记录的人工接收人数量为0，但这只表示缺少接收记录，不能推断任务实际从未被任何人查看。

### 5.3 典型案例分析

**案例一 原始配对中的mergesort多轮闭环。** 使用 `run-5feb3a0bf6824b90a6a0ff634db6b488`。基线1/14通过；第一、第二轮候选仍为1/14；检测员解释运行错误，模型调度员提出建议，程序决定定位，定位接收检测输出和批准指令后回修复员。第三轮开发14/14，随后干净最终复验14/14。修复员3次、检测员3次、调度员2次、定位员2次，共10次模型请求。应展示两次回流、引用证据ID及候选版本，避免只画流程箭头。单Agent同题也在3轮后通过，故本例用于展示机制，不用来证明多Agent更有效率。

配图可用 `../../evidence/single-multi-agent/111/figures/mergesort-self-loop.png`。RPC桥接栈出现在测试证据中，模型的根因推测不是工具事实；不能把所有运行错误都写成算法错误，也不能把相同候选重复提交说成持续改进。

**案例二 原始next_palindrome达到上限并产生人工复核材料。** 多Agent原运行 `run-ab4b130887334208bcc51dee6fd39262`，前两轮候选均为4/5，第三轮修复输出把同一路径列出多次，被协议校验拒绝，没有产生第三份可执行候选。系统在3轮上限处停止并生成handoff.json，状态pending_human，accepted_by为空，final未执行。失败同时涉及候选缺陷与输出协议，应结合校验错误和末次工具证据分析，不能仅写代码复杂导致失败。

本次恢复运行 `run-17496b4c92ce4911a42be3b8d03c0c81`另列：前三轮开发为4/5、4/5、5/5，最终5/5；四角色实际调用3、3、2、2次。它展示后续新任务能够修复，但不能倒写原任务为成功，更不能声称平台自动完成了人工接手。

案例复核材料至少包含原始代码与最终diff、每轮测试计数、检测分析、模型建议、程序裁决、定位交接、最终复验、结束原因、费用和时间。没有记录的具体输入输出示例不要让模型补造。

### 5.4 结果讨论

收益可以写成：测试证据和版本校验让角色协作可追溯，部分失败候选能够经过有界反馈转为通过；规则守卫阻止模型建议越过权限、预算或工具结论。机制价值包括可解释停止、错误分层与可供复核的材料，而不是无条件提高正确率。

代价应同时呈现：多Agent平均请求2.450次，单Agent1.225次；平均任务耗时分别39.437秒和34.161秒。多Agent的已知费用小计已高于单Agent，但仍有费用待核对，不能报为精确完整账单。Token缺失和失败请求应保留，不把思考Token再次加到已含它的输出Token中。

已返回usage的Token统计如下，多Agent还缺两条请求的用量，因此其合计只是已知小计，不能当作完整总Token：

| 用量字段 | 单Agent | 多Agent |
| --- | ---: | ---: |
| 有usage的请求 | 49 | 96 |
| 缺usage的请求 | 0 | 2 |
| 已知输入Token | 130005 | 224131 |
| 已知输出Token | 12596 | 25651 |


适用场景是已有可执行测试、修改范围明确、可持续取得工具证据的受控修复。对很容易的缺陷，额外角色可能增加开销；对测试覆盖不足、真实依赖复杂或服务不稳定的任务，更多Agent不能代替环境治理和测试设计。当前为规则式分支与模型建议协同，不是自主学习调度；后续需要等调用预算的机械重试组、失败类型分层、多次重复和未见任务来评价净收益。

## 四 总结与展望的建议内容

### 6.1 研究工作总结

建议总结为：围绕受控Python缺陷修复，实现四角色合同、版本和证据校验、条件调度、有界反馈、隔离测试与干净复验，以及停止材料和结果查看。完成40题80条配对，并保留5条非成功首试；三题独立恢复均通过，形成40题逐题成功覆盖。贡献重点为工程闭环和可复核证据，不预设编排总体优于基线。

### 6.2 当前局限

应保留原生测试覆盖有限、公开题可能被模型接触、单源文件场景、没有自主学习调度、独立外部用户与并发压力数据不足、单次采样和服务网络影响等限制。人工复核包已具备，但接单与签收链未验收。新网络方案的本机真实HTTPX测试与真实付费恢复运行分开描述，不能用自动测试项数代替修复成功题数。

### 6.3 后续拓展方向

1. 优化现有LLM调度建议与程序约束的协同，研究代价感知或学习式策略。当前已有模型调度Agent，不宜写成未来才首次引入。
2. 新增测试生成Agent，区分开发测试与冻结最终验收，防止修复员通过修改测试降低标准；该能力尚未实现。
3. 接入Defects4J开展更大规模验证。它是Java真实缺陷基础设施，不能直接当成当前Python适配器的扩容；需增加JDK、构建/依赖、测试工具和隔离镜像适配。依据[官方仓库](https://github.com/rjust/defects4j)。
4. 用静态分析辅助定位，例如AST、调用关系和既有工具的受限输出，与动态测试证据交叉核对；不宣称当前已具备成熟全仓库静态分析。
5. 接入用户样本、补齐人工处理工作流、重复实验、跨模型和真实仓库验证。所有未来能力使用拟、计划、待验证等措辞，不放在实现完成列表。

## 五 用户自有样本的架构拓展方案

本轮已确认只写方案，不开发。首版建议支持单个Python源文件和用户提供的pytest测试文件，通过受限任务适配器进入现有闭环。架构图在用户入口与任务登记间增加虚线框“自有样本接入 拟实现”，随后才连接现有配置检查、基线、修复、检测、分支和最终复验。

输入必须包含目标描述、源码、测试及必要版本约束。限制大小、数量、扩展名与路径，拒绝路径穿越、压缩包符号链接和任意安装脚本；不允许上传后在用户电脑直接执行。用户测试本身也可能是恶意代码，不能未经隔离就作为可信测试基础设施执行。应冻结源码、测试与环境身份，标记这是用户提供测试，不等同基准可信标准。

先做不付费基线：未复现缺陷时说明测试不足或代码已满足给定断言，不自动消费模型修复；没有可执行测试时提示补充，不假装验证通过。修复员只可修改允许的源码，测试只读，依赖使用预批准离线集合，执行隔离与资源限制沿用现有边界。

建议后续验收包括正常样本、恶意源码、恶意测试、路径与大小拒绝、缺依赖、超时、无测试、基线全通过、测试保护、费用停止、最终复验和导出。多文件仓库、自动依赖安装和测试生成另批扩展。

## 八 可用于答辩的简短讲解

闭环怎么决定下一步：每个有效候选先接受真实隔离测试，检测员解释当前证据，必要时由模型调度员建议动作，程序按证据和预算裁决。定位必须拿到检测输出和批准指令，才能把分析交回修复员。成功必须经过干净最终复验，失败到上限就停止并生成复核材料。

多Agent是否比单Agent更好：这批配对没有显示总体成功率优势，单组38/40，多组37/40，多组请求和时间更高。但我们有实际可追溯的协作回流与停止证据，也看到单题不同结局。我们报告代价和失败，不用跨版本补跑制造增益；后续将按失败类型及等资源重复实验判断适用条件。

为什么还要人工：模型输出可能无效，环境和预算也可能不允许继续。平台已经生成可供人工判断的材料，但没有假定有人已经完成复核。人工接单、处理和签收链是下一阶段功能，生成移交包比例与真人介入比例分开统计。

样本能否自己上传：当前版本只支持登记任务。下一步拟增加单文件Python加pytest测试的受限接入，先冻结测试并执行基线，再进入现有闭环。自有测试的可信性与隔离需单独设计，不把它当生产仓库通用修复已经完成。
