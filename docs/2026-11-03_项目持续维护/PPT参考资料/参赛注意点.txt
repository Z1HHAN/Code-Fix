证据驱动的多 Agent 编排与验证平台
参赛注意点
一、赛道一评审重点
赛道一不看你是否能修复100%的bug，重点看这几点：
1. 角色解耦：多个 Agent 有清晰独立职责，不是多个一模一样的 Agent；
2. 编排逻辑：有顺序流、分支判断、重试节点；
3. 协同机制：Agent 之间传递结构化消息（缺陷描述、代码片段、日志、报错信息）；
4. 可观测性：每个 Agent 输出中间结果，工作流全程可追溯；
5. 效果验证：在公开缺陷数据集上做批量测试，统计指标（修复成功率、编译通过率）。
二、参考数据集
优先：QuixBugs（轻量，Java/Python 小缺陷，适合快速批量测试，样本不大，容易跑）
备选：Defects4J（标准软件工程缺陷数据集，样本多、偏工程化，可赛后拓展用）
评价指标：补丁编译通过率、可正确通过测试用例的修复成功率。
三、项目全程重点注意事项
（一）方案与边界把控（最容易踩坑）
1. 分清调度器定位：调度是编排平台自带的条件判断节点、全局变量计数（retry_count），不是一个独立 LLM 智能体。申报、报告、答辩都要讲清楚：采用规则式证据调度，避免评委误以为你们训练了决策模型，也避免实验引入额外混杂变量。
2. 测试用例边界严格收紧：参赛阶段不做 Agent 自动生成测试用例。测试脚本全部来自 QuixBugs 数据集自带 test.py，测试 Agent 只负责执行脚本、抓取报错信息、输出标准化 JSON 证据。自动生成测试仅写在 “未来拓展”，不纳入当前主干流程。
3. 重试机制必须有上限：设置最大重试次数（推荐 2 次），到达上限直接流转人工复核分支，杜绝无限循环。人工复核是兜底出口，不是可有可无的装饰。
4. 对照实验必须保证单一变量
两组使用完全相同的 Agent 提示词、大模型、数据集样本、测试脚本；
唯一变量：调度策略（固定线性流水线 / 证据驱动闭环调度）；
两套独立编排流，不要在同一个工作流里切换模式，防止互相干扰。
5. 样本规模控制合理：只用 QuixBugs 的 Python 子集（40 + 样本），不要强行上 Defects4J。
人力、时间有限，优先保证实验可复现、流程跑通，而不是样本数量巨大。
（二）编排平台与 Agent 输出规范
6. 所有 Agent 强制结构化 JSON 输出，减少自由文本。调度节点依靠 JSON 字段做判断，自由文本极易出现解析失败、分支不触发。
7. 统一全局变量，每次进入重试分支前先计数 + 1，记录每一轮中间结果，方便溯源和报告展示。
8. 日志留存：每一轮定位文本、补丁 diff、测试证据、分支跳转记录全部保存。答辩要看流转过程，实验复现、失败案例分析也依赖日志。
9. 区分两套编排画布：实验组（闭环重试）、对照组（一轮即终止），截图分开保存，答辩 Demo 分别演示。
（三）指标、统计与实验严谨性（评审重点）
10. 固定评价指标，全程不变：
主指标：修复成功率（补丁通过数据集全部原生测试用例）
成本指标：单样本平均 LLM 调用次数、Token 消耗、平均耗时
过程指标：平均重试次数、移交人工复核的样本占比
11. 禁止选择性筛选样本：必须使用同一批样本跑两组实验，不能实验组挑简单 bug、对照组挑难 bug。
12. 失败案例要分类分析：定位错误、补丁引入新 bug、测试本身存在边界缺陷、大模型幻觉等，不要只放数字，要有定性分析。
（四）申报书、报告、答辩话术要点
13. 创新点落脚点放在编排调度范式，而不是代码修复能力。赛道一不比拼 bug 修复率有多高，重点看多智能体的编排、流转、闭环验证思路。
14. 提前准备 Demo 演示脚本：分两段演示，一段演示成功闭环迭代、一段演示重试耗尽转入人工复核，同时展示对照组一次性流程。
15. 客观陈述权衡关系：证据驱动调度可以提升修复成功率，但会增加调用成本、耗时。不要只说优点，主动说明取舍，学术观感更好。
16. 区分 “参赛实现版本” 和 “后续研究拓展”：拓展方向（独立调度 Agent、自动生成测试用例、引入静态分析、迁移 Defects4J）统一放在展望，不要混进当前实现。
（五）其他避坑点
17. 不要过度增加 Agent 数量：主干就定位 Agent、修复 Agent、测试 Agent 三个智能体，再加平台调度节点、人工汇总节点即可，角色过多会让流程臃肿、调试成本暴涨。
18. 代码执行风险：Python 测试脚本建议本地轻量脚本运行，不要依赖平台沙盒执行代码，沙盒容易有环境、权限、超时限制。
19. 版本可复现：记录大模型版本、随机种子、样本清单、提示词原文，全部放进附录。
