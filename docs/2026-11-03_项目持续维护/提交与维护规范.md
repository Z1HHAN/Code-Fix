# 提交与维护规范

维护基线：2026-11-03。按A本次明确要求生效，替代原“每日新建daily/分支交付文件”的规则。11月3日是固定入口标识，后续11月4日、5日及以后仍维护本目录，不滚动改名，不另建日期计划、日期台账或日期交付说明。真实日期写在记录字段里。

## 一项信息只维护一处

| 信息 | 唯一维护文件 | 更新时机 |
| --- | --- | --- |
| 实现、测试、独立验收状态、证据、阻塞、下一步 | [当前开发任务台账](当前开发任务台账.md) | 对应任务有可靠新证据时；三种状态分别填写 |
| 优先级和前置条件 | [当前开发计划](当前开发计划.md) | 任务完成、阻塞或范围获确认时；沿用T-ID |
| A/B/C任务分工与交接 | [任务分配与交接](任务分配与交接.md) | 责任或交接条件变化时 |
| HTTP/输入输出/角色契约和路径 | [接口与路径规范](接口与路径规范.md) | 已授权接口或路径实际变更的同一提交 |

| 项目级里程碑 | [CHANGELOG](../../CHANGELOG.md) | 实际合入后追加概述，引用上述记录 |

当前规范、需求、UI和测试说明均在本固定目录内维护；不可变V3原文、C原包、审计与运行原始证据保留其明确登记的原位。文档修订不把组件版本0.2改成3，也不把历史测试日期改成当天。不得为“刷新GitHub备注”改写旧提交；列表备注是最后一次真实提交说明，状态以台账为准。

## 每次拉取与修改

1. 先检查工作区；保留自己和他人的未提交修改。记录拉取时间、分支、实际main SHA、任务T-ID和认领范围。
2. 新工作从最新main建立`codex/<角色>-<主题>`分支；已有共享分支不重写历史。下面名称只是示例，不带日期也可正常追溯。

```powershell
git status --short
git switch main
git pull --ff-only origin main
git rev-parse HEAD
git switch -c codex/b-runtime-review
```

3. 新增功能仍按[AGENTS](../../AGENTS.md)先向A说明影响及验收条件并获确认。旧计划不是自动开发授权；已批准范围无需重复询问。文档状态登记不能夹带新功能代码。
4. B交实现与本人测试；C对明确的被测代码commit复跑，并写明独立机器或同机复核；A核对证据后登记总状态。不能代签B/C，不把“已装Docker”记成资格通过，不把参考答案检查记成真实模型修复。

## 每次提交与推送

所有正式提交的标题使用`类型(范围): 具体动作`，类型为`feat/fix/test/docs/chore`；合并用`merge`。例如`docs(maintenance): 统一固定维护入口与提交记录`。提交正文写任务ID、改了什么及原因、验证命令与结果/证据、未覆盖范围。一个提交围绕一个目的，不混入密钥、缓存、参考答案、无关重命名或旧证据改写。

每次提交在同一份[持续交付与变更记录](持续交付与变更记录.md)追加下面的记录；同一任务多次提交用不同记录ID，不覆盖旧结论。可先提交代码，再在记录中绑定该已存在的代码commit；文档提交本身由Git追溯，不要求正文填写自身SHA。纯文档提交写文档范围与静态核验，不虚构pytest新成绩。

```text
### 记录ID：角色-主题-序号
实际时间/作者/角色/机器：
拉取时间/工作区状态/分支/main基线SHA：
任务T-ID/旧ID别名/本次认领范围：
被测代码commit/测试套件/配置/提示词/镜像版本：
本轮原问题→改动→行为，关键文件：
实现状态 / 开发测试状态 / 独立验收状态（各自范围）：
原样命令 / 实际退出码 / 通过失败跳过 / run_id：
可访问日志/JUnit/报告/截图/ZIP与SHA256：
验证类型：平台、可信夹具、模拟、Docker资格、公开基线、真实模型、参考、文档
费用/模型授权来源，未知金额unknown；无调用写未调用：
失败/阻塞/遗留/下一步/下一负责人：
A需同步的T-ID及原状态→建议状态/依据/文件（无变化写无需同步）：
```

推送前检查diff、相关命令/链接/路径和状态依据；按[PR模板](../../.github/pull_request_template.md)引用本日志记录ID。无PR权限也提交同样记录供审核，不强推绕过保护。B/C推送自己的分支，A或获授权者复核后正常合并main，再核对远端SHA。收到分支不等于已合入，合入不等于稳定版本或本人签收。

## 每次合并后的同步

A按相同被测commit的证据核对台账三种状态，补证据/阻塞/下一步和最近核对日期；完成项从待办索引退出并链接已完成索引，未完事项沿用原ID在原表更新。调整计划、交接及受影响规范，追加本日志、CHANGELOG与素材索引；无变化明确写无需同步。入口改变同提交修复当前链接与路径表。不存在后台自动同步器、Git hook或CI强制拦截，本规范由提交者和复核者逐项执行。

证据只新增独立run_id，不覆盖旧结果；失败后复跑也保留初次失败。原始证据可以含真实时间，通常放`evidence/<主题>/<run_id>/`，本机临时内容放被忽略的`runs/`。这与禁止新增每日权威文档并不冲突。仅本机runs路径不能算已交付证据。模型/预算/隔离未经确认仍记未运行或受环境阻塞；mock必须标模拟。

多成员同时追加同一日志发生冲突时，保留双方完整记录及原ID，按实际时间排列；不得用一方覆盖另一方或丢弃失败记录。合并后再次核对记录ID唯一性与证据版本。

历史记录统一从[历史索引](../99_历史归档/历史归档索引.md)查阅，仅供原结论追溯。历史文件中的旧流程不再是当前指令，原文字节在治理快照/Git可查；不新建daily、deliveries或按日期分立的当前文档。

## 新交付的分类接收

B/C后续不得再在仓库根目录新增`C_日期交付`等打包目录。可运行脚本归`scripts/`，测试归现有对应测试模块；有明确相对路径依赖的独立验收包保持原模块结构，并在接口与路径规范登记。原始证据归`evidence/<主题>/<run_id>/`，原始交付包和历史补丁归`docs/99_历史归档/`既有主题，当前需求/状态继续更新固定维护入口。接收者先核对SHA、原版本、依赖、重复与冲突，再提取有效信息；旧补丁不得覆盖当前文档，原始失败不得改写，归档须留旧新路径映射。接收、复跑、合入和签收分别登记，不以日期更新替代真实验收。
