# B/C分支提交与版本记录规范

11月2日按A新增要求制定。目的：B/C每次拉取后交分支，都能说明“做了什么、如何证明、还缺什么、A改哪些状态”，并为后续PPT和demo保留来源。规范从本次交付开始，不追补编造旧日成绩，不代签B/C。

## 最少交付三样

1. **可核对的代码/文档commit和分支**：说明基于哪个main、改哪些文件、对应任务和功能编号。
2. **一份分支交付记录**：复制[模板](templates/BC分支交付记录模板.md)，保存为`docs/deliveries/YYYY-MM-DD-B或C-主题.md`。同一分支多次交付可追加有时间/commit的记录；旧证据不覆盖。
3. **原始证据或可访问链接**：运行命令、真实结果、日志/JUnit/报告/必要截图。仅做文档也说明检查方法；不能只写“已完成”“跑通了”或只给截图。

每次有新代码供别人复核，或收工交接，即算一次交付；纯本地探索不用每个临时commit写长报告。交付记录可短，但下面字段不可缺。使用[PR模板](../.github/pull_request_template.md)填写摘要；无PR权限时在分支中提交同一记录，并交分支/commit供复核，不能跳过审核或强推。

## 拉取与分支

先检查`git status --short`；有未提交改动先妥善保存，不用reset清空。新任务从最新main派生，已有共享任务分支不随意重写历史：

```powershell
git switch main
git pull --ff-only origin main
git rev-parse HEAD
git switch -c codex/b-20261103-runtime
```

上例为B的新分支示例，C改用`codex/c-20261103-tests`；如已存在则选择新的主题/后缀，不删除旧分支。实际名称与基线SHA填写记录。首次交付前按项目README准备依赖，不凭自己的旧环境推定仓库可复现。

提交使用`feat:`、`fix:`、`test:`、`docs:`、`chore:`加具体动作，如“fix: block new calls while prior-day cost is unknown”。一条提交聚焦同一目的；代码、必要验证和对应说明一起交，不混入无关重命名、密钥、缓存或历史证据改写。最后正常推送自己的分支，不直接覆盖main。

## 每份记录写清七件事

| 必填项 | 写法 |
| --- | --- |
| 交付身份 | 日期、B/C、任务ID（如N03-03）、功能ID（如F10）、分支、基线main SHA、被测代码commit |
| 做了什么 | 原问题/触发条件、修改后具体行为、关键文件；只写本人本轮新增，不把已有实现重复算新成果 |
| 验证了什么 | 原样命令、执行机器/环境、实际退出码与通过/失败/跳过、对应代码/测试版本；未运行写原因 |
| 证据在哪 | run_id、日志/JUnit/JSON、diff/报告/ZIP/哈希及可访问位置；不能只写本机被Git忽略的runs路径 |
| 能力边界 | 平台单测、可信夹具、Docker资格、公开基线、真实模型、mock、参考检查、故障注入分别标明 |
| 还差什么 | 失败/blocked/待验、新问题、依赖、下一位接手人；不把安装Docker、组件通过当真实闭环完成 |
| A更新哪些文档 | 功能ID、原状态→建议新状态、依据记录/commit/run_id、受影响文件清单；另写PPT/demo能用的一两句话和素材位置 |

记录中的`code_commit`填已存在的被测代码提交：可先提交代码，再提交交付说明；不要要求同一提交的正文写出自身SHA。最新分支HEAD/合并提交由Git或PR页面确认。代码在C复核后又变更时，说明受影响范围并重新验证；旧结果只能支持原commit，不能直接签新代码。

## B、C、A分别做什么

- **B**：交实现及本人验证；列出启动方法、配置差异、兼容影响、已知问题和对应证据。新增入口/模式必须同步运行文档；没有实现的命令不先写成可运行。
- **C**：针对B明确的commit复跑，交独立记录并链接B交付；记录实际执行位置，是C独立机器还是B隔离机同机复核。未运行/不能复现/软链接权限跳过如实写，不替B写实现完成或替A批准费用。
- **A**：先检查“commit一致、证据可访问、结论与范围一致”，再按下表更新。未合并先记“分支已交付/待复核”，只有通过限定范围审核并正常合入后才在主线变更日志登记为已合入；不因收到了PR就写功能已完成。

B/C先在自己的交付记录列“建议更新”，若其代码改变现有运行命令需同步修正文档；A合并时集中对齐总状态，避免三人同时手改多份总表造成相互覆盖。没有变化写“无需同步”，不要空着让A猜。

## 证据与版本口径

- 关键脱敏材料可放`evidence/<日期>/<角色>/<run_id>/`，配SHA256索引；旧批次原字节保持不变。大记录用团队可访问位置并写访问方式/哈希；密钥、账本凭证、个人会话和参考答案不随分支交产品Agent。
- 真实模型记录适用时附模型/参数、用量、费用口径和授权来源；未知费用写unknown，不能用0掩盖。任务测试、镜像/测试套件、补丁/代码版本各自可追溯。无真实请求就明确“本轮没有真实模型调用”。
- PPT/demo标“现场”“历史真实回放”“明确模拟”之一；已导入40题、167项平台测试、闰年3过1败均不得改写为模型已修复40/167题。
- `CHANGELOG.md`为统一变更日志，交付记录是原始来源，素材索引只指向来源，不复制一套相矛盾的成绩。模板和空台账不算完成证据。
- 稳定/开发标签仅在准确提交、范围和验收明确后创建，不以日期或计划自动升级版本。新一天新增台账；已知历史问题即使后来修复，也保留旧版本当时结论。

本次增加的是文档规范、模板和手工核对流程，未实现Git hook或CI自动拦截；缺交付记录按规范不得记为已复核交付，由A/B/C在合并前检查。
