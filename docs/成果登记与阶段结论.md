# 成果登记与阶段结论怎么填

A代替E，B和C提供真实数据。先记录事实，再写结论，不靠文件名和截图推断程序完成。

## 一次运行登记一次

evaluation/run_record.template.json是空模板，不是真实运行。
由B的程序生成实际记录，A登记到任务台账；暂未实现自动汇总时A根据原始证据手动汇总，但不能补造events.jsonl。
实际JSON保存到本地runs/<run_id>/，关键记录检查敏感信息后可放evidence/<run_id>/并加入仓库。
模板中的template_only在真实记录中删除或设为false；run_id和版本必须真实，不能照抄样例。
实际记录终态字段统一为status，与RunSummary一致。limits_snapshot.daily_cost_limit为全队北京时间当天累计上限；max_tool_calls为单次运行上限并含模型请求和网络重试。费用账本跨run累积，不能新建运行后清零。

| 字段 | 从哪来 | 不知道怎么办 |
| --- | --- | --- |
| run_id、任务ID、系统提交、配置版本 | B程序和Git | 找B，不猜 |
| 任务来源、固定commit、允许路径、环境资格 | C记录 | 写未确认 |
| 任务起点与修改后版本 | B/C计算 | 缺少则不能证明证据对应 |
| 开发测试结果 | 执行器真实输出 | 未执行写not_run，不能填0失败就算通过 |
| 独立验收结果 | C干净副本的评测 | 未执行写not_run；错误或超时为inconclusive，不是passed |
| 模型原始回复和修改 | B本次运行文件 | 没有就登记证据缺失 |
| 调度动作与触发证据 | Decision与Evidence | 不能只凭页面文字 |
| 费用、Token和耗时 | API用量/执行日志/明确计费来源 | 费用未知写unknown、金额null，不能写0 |
| C复核结论 | C实际检查 | 未检查写not_run |

run_type必须区分：
- model_repair：真实模型修复尝试。
- reference_check：参考答案或参考补丁环境验证。
- fault_injection：人为设置错误以验证平台控制。
- tool_check：已知补丁等工具通路检查。
- human_reproduce：A按说明复跑。
后三类不混入公开任务模型修复率；人工参考验证也不算模型成绩。

## 晚上阶段结论 填docs/day2_decision.md

1. 先填平台和配置的准确版本。
2. 已完成：只列有证据支持的功能；输入材料写“材料已准备”，不要写“功能已完成”。
3. 未通过/未运行：列出缺口、负责人、下一步和检查时间。
4. 逐项看真实闭环、分支、停止、权限、版本、知识、独立验收、他人复跑。
5. 决定继续、缩减或暂停自动执行，说明具体原因与边界。
6. B/C看过技术事实后，A确认。导师摘要可直接从该结论摘录，不另编成绩。

继续：隔离可用，轻量闭环、证据分支与停止有效，其他缺口有计划。
缩减：轻量主链路可用但复杂仓库/界面等受阻，保留已有能力，明确延后内容。
暂停自动执行：隔离或状态管理不可用，或仍无真实执行与测试证据，先修执行器，不扩大任务。
模型修复失败不等同于执行器坏了；真实失败也应保留，不能只挑成功案例。

## 版本更新怎样留记录

同一任务、模型与预算下，升级前后分别留run_id和系统commit；不要拿不同任务的成绩声称版本提升。
预算未确认不批量运行。本轮三题只用于基建与初步尝试，不做统计领先或百分比提升结论。
一轮小样本对比不足以证明动态流程更好。正式三组对照需后续冻结任务与口径。
