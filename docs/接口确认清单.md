## 今天怎样确认 不只发一句“收到”

1. A把任务、角色、规则和本清单发给B/C。
2. B逐个读取三个新JSON配置，确认能解析；指出无法实现的字段，不偷偷忽略。
3. C用样例结果交给B，B把结果变成Decision；双方确认每个字段含义。
4. 切到一次真实闰年测试，由C执行器产生结果，再由B程序读取；检查路径能打开、代码版本对得上。
5. 分别用断言失败、环境异常、上限触发检查后续动作；只解析JSON还不算接口接通。
6. A/B/C在同一个PR或Issue写确认，记录准确提交编号，才冻结为0.2。未确认前保留draft，不能并行静默改名。

## 状态分开 别混成一个“成功”

- ToolResult.status：ok / failed / timeout / blocked，表示工具状态。
- verification_status、dev_result、final_result：passed / failed / not_run / inconclusive，表示验证结论。
- RunSummary.status：success / failed / stopped / infra_error，表示终态；暂停时程序保持非终态并记录事件。
- evaluation/run_record.template.json使用同名status；与RunSummary的共有字段含义一致，另外保留审计字段。
- limits_snapshot.daily_cost_limit与规则同名，表示全队北京时间当天累计费用上限，不是单次任务金额。max_tool_calls为单次运行上限，包含模型请求、网络重试和执行工具调用。新建run不得重置当天费用账本。
- exit_code非零不能单独证明业务断言失败，要看收集、导入、依赖及代码异常来源。
- 开发passed并不等于final_result passed。只有实际独立验收且代码版本对应才允许最终success。
- final_result未运行就写not_run；不能因为开发4/4通过而复制成passed。

## 和v0.1怎么衔接

不要覆盖旧任务和day1-kit提示词。v0.1保留复现，v0.2使用根目录新配置与prompts/。

| 旧约定 | v0.2约定 | 谁处理 |
| --- | --- | --- |
| ToolRun | ToolResult | B/C写兼容适配或共同升级，不能只换文档名 |
| status=passed | status=ok，verification_status=passed | B/C明确转换 |
| status=failed | 分清断言失败、代码异常和环境失败后填相应状态 | C提供原始证据 |
| error | blocked；验证按是否开始填not_run或inconclusive | B/C确认 |
| log_path | stdout_path、stderr_path | C执行器写真实路径 |
| 缺少版本 | code_version及run_id、task_id | B/C补，不猜测 |
| Decision.evidence | evidence_ids数组，引用Evidence ID | B生成可追查证据 |
| rounds_left | retries_left，均指剩余候选修复轮数 | A/B定语义 |
| max_repair_rounds | 新TaskSpec.limits.max_repair_rounds | B适配；全局与任务限制取更严格者 |
| 任意test_command | C预登记test_profile对应的固定argv | 模型不能修改命令或添加--correct |

模型输出也有改动：v0.1修复员返回裸代码，v0.2根目录修复员返回JSON changes/new_content及说明。
B必须使用对应版本的解析器；不能把JSON全文当Python文件写进去。工具写入前检查路径、软链接与权限。

## B实现规则解释器要知道什么

decision_rules.json的when是“字段全部相等”。按数组顺序命中第一条；未匹配暂停。
由执行器/分类器计算下列字段，模型不能直接决定：
- 这些必需上下文字段缺失、类型错误或隔离未知时，先拒绝推进，不能靠未命中第一条规则绕过检查。
- phase：development或final_check。
- failure_class：passed、assertion_failed、syntax_error、code_runtime_error、environment_error、timeout、permission_violation、model_transport_error、invalid_model_output、heldout_failed、not_reproduced等。
- isolation_ready、user_pause_requested、evidence_matches_current_version。
- repair_budget_available、execution_budget_available、needs_new_repair、next_action_requires_execution_budget。
- output_agent：模型输出的来源角色，非模型输出证据为null；由程序确定，不能让模型自报。
- needs_new_repair仅根据当前有效开发证据计算；代码更新但未测试时必须为false，不能因已用完修复轮次跳过最后一个候选的测试。

超时清理和有效独立验收终态优先于普通暂停请求。所有Agent恢复规则只处理development阶段；final_check异常只能结束或交C核查。陈旧的通过和失败证据都不能终结当前版本，须在预算内重验。定位员输出无效暂停查协议；只有修复员输出无效才按剩余修复预算重修。

规则在已存在证据上决策；每个新模型请求、工具执行、重新测试前仍须统一预算闸门检查。
已合法完成的最后一次验收即使刚好耗尽预算，也不应被后续“发起新动作”的预算闸门改写成失败。
达到上限不允许额外“免费重试”；网络重试必须独立有界。
环境异常优先确认来源：待修文件语法错归syntax_error；测试/依赖配置问题不能靠改业务代码处理。
代码补丁改变code_version后旧验证立即失效。暂停后要重新核验候选补丁与新约束。
final_check未准备、超时、错误或未知时，不能宣布success，且保留测试细节不能传给Agent。
