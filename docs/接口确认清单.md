## 本轮角色与目标测试边界

- locator、repairer是LLM角色；tester是确定性测试执行与证据整理工具，不增加测试LLM；reviewer保持关闭。tester由control调用，role_type=deterministic，model/prompt为null；execution_binding=null、implementation_status=planned表示仍未接线。
- QuixBugs使用固定版本的原生测试。Agent不能生成、删除、修改目标测试，不能改测试命令、添加--correct或读取正确实现。C先登记测试文件、测试ID、test_suite_version、expected_test_count、允许跳过项及原因。
- 独立验收指C从干净起点应用系统输出补丁，再独立重跑同一套固定原生测试。它验证补丁可复现，不代表隐藏测试或额外覆盖；开发通过和独立验收仍分别登记。
- 平台自身的fixture、协议测试和故障注入可以由B/C编写，必须与目标测试和model_repair成绩分开。QuixBugs默认跳过的慢测试须如实登记，不能写成所有原生测试都已执行。

## 怎样确认 不只发一句“收到”

1. A交付任务、角色、规则和本清单；B/C在同一PR或Issue列出可实现字段、适配差异及未决项。
2. B解析配置、C提供一个独立call_id的ToolResult样例，双方核对字段含义和文件组织。解析样例只算协议检查。
3. 先用人工已审查的固定fixture检查补丁应用、零测试、错误、超时和已验证范围内的进程退出；完整进程树清理未验就标待验。已有缺陷整改须附复验结果，不能凭“已通知修复”打勾。
4. C可直接调用执行工具跑一条已审固定fixture，由B读取实际ToolResult；核对run_id、call_id、代码版本、测试套件版本和原始证据。此类直接工具联调记tool_check/fault_injection，不绕过或伪填调度器R00，不代表隔离或模型闭环已通过。自动执行模型候选须另行确认隔离与运行预算；未实际执行的检查标待验。
5. 断言失败、环境异常、上限与动态分支的执行检查按[五天计划](五天落地与参赛分工-20261101至1105.md)推进；11月1日可用fixture核对契约，但不能据此宣布完整动态编排已完成。
6. A/B/C对同一准确提交确认后，只冻结已验证的内部契约范围，记录仍待完成项。HTTP、UI或未跑通字段继续保持草案，不能并行静默改名。

## 状态分开 别混成一个“成功”

- ToolResult.status沿用ok / failed / timeout / blocked，表示工具状态；不要把error或passed加入这个枚举。
- verification_status、dev_result、final_result沿用passed / failed / not_run / inconclusive，表示验证结论。
- RunSummary.status沿用success / failed / stopped / infra_error，表示终态；暂停时程序保持非终态并记录事件。
- [运行记录模板](../evaluation/run_record.template.json)使用同名status；与RunSummary共有字段含义一致，另外保留审计字段。
- limits_snapshot.daily_cost_limit为全队北京时间当天累计费用上限；max_tool_calls为单次运行上限，包含模型请求、网络重试和工具执行。新run不得重置当天费用账本。
- 非零退出码不能单独证明业务断言失败；要区分收集/导入、依赖、业务代码异常与测试断言失败。
- 未执行为not_run；已开始但超时、执行错误或证据不完整时按来源记inconclusive，不能通过。开发passed不能直接复制为final_result passed。
- 最终success须实际独立验收通过，且代码版本和冻结测试套件对应。通过仅表示通过已登记的测试范围，不证明程序完全正确。

## 每次测试结果至少要交什么

以下为本轮提案，字段位置与解析器仍须B/C对同一提交确认，旧生产者不会因文档更新而自动适配。

| 字段 | 含义与缺失处理 |
| --- | --- |
| run_id、task_id、call_id | 一次运行、一个任务、一次调用的真实标识；每次调用及重试独立留产物，不能覆盖上一次结果 |
| phase、code_version | development或final_check；绑定实际被测代码版本，不能复用上轮通过记录 |
| test_suite_version、expected_test_count | ToolResult顶层字段：测试套件冻结版本与预期收集数量；C确认实际含义和计算口径后才消费 |
| counts.collected、counts.passed、counts.failed、counts.errors、counts.skipped | 增加collected与errors；收集/初始化/清理错误不能丢失为0失败。不可用时填null并说明原因，不得猜0 |
| exit_code、status、verification_status、failure_class | 保留退出码和分类依据；未知不能由“日志没有FAILED”推断passed |
| stdout_path、stderr_path、junit_path、junit_missing_reason | 独立call_id对应原始文件；后两项位于ToolResult顶层。JUnit缺失时junit_path=null并说明原因，依赖JUnit的统计填null，不能伪造文件或把缺失当通过 |
| duration_ms及超时/清理证据 | 如实记录实际耗时、进程退出及已检查的清理范围；完整进程树未验标待验，不能声称全部清理。清理异常交人工处理 |
| output_agent | 确定性执行器输出为null，不能冒充模型角色 |

判定通过前应核对退出码、有效测试数量、预期套件覆盖、失败/错误数量及允许跳过项；collected=0、数量不符或统计来源缺失时不能自动通过。pytest的清理错误可能与测试结果重叠，不能简单靠计数相加证明完整性。允许跳过项须预先冻结并单列，不能写成全部测试已执行。

## 和v0.1及旧记录怎么衔接

不要覆盖旧任务、day1-kit提示词或已有原始记录。v0.1保留复现，v0.2使用根目录新配置与prompts/。

| 旧约定 | v0.2提案 | 谁处理 |
| --- | --- | --- |
| ToolRun | ToolResult | B/C写兼容适配或共同升级，不能只换文档名 |
| status=passed | status=ok，verification_status=passed | B/C明确转换并保留原始值 |
| status=failed | 分清断言失败、代码异常与环境失败 | C提供原始证据 |
| error | status按原因转blocked/failed等合法值；验证按是否执行填not_run/inconclusive | B/C确认映射，不能机械改名 |
| log_path | stdout_path、stderr_path | C写真实独立调用路径 |
| 缺少版本、统计或JUnit | 新记录补齐；旧记录注明不可得及原因 | 不反向伪造旧记录 |
| Decision.evidence | evidence_ids数组 | B生成可追查证据 |
| rounds_left | retries_left，表示剩余候选修复轮数 | A/B/C确认计数边界 |
| max_repair_rounds | TaskSpec.limits.max_repair_rounds | 全局与任务限制取更严格者 |
| 任意test_command | C预登记test_profile对应固定argv | 模型不能改命令或添加--correct |
| failure_class=heldout_failed | 新提案canonical值final_check_failed；旧值作为读取兼容别名 | B/C确认适配器、规则和UI，保留旧原始值与解释 |

final_check_failed表示当前版本在独立重跑原生测试时确认失败，不表示运行过隐藏测试。超时、环境错误或缺少证据仍按各自原因分类，不能统称验收断言失败。旧heldout_failed只作兼容，不改写已有运行文件，也不倒推旧运行的测试覆盖范围。新旧失败规则都须受final_check阶段与当前代码版本匹配保护；兼容迁移仍待B/C确认。

模型输出也有改动：v0.1修复员返回裸代码，v0.2根目录修复员返回JSON changes/new_content及说明。B须使用匹配解析器，不能把JSON全文当Python写入。工具写入前检查路径、软链接与权限。

## B实现规则解释器要知道什么

decision_rules.json的when是“字段全部相等”，按数组顺序命中第一条；未匹配暂停。上下文由执行器/分类器计算，模型不能决定：

- 必需上下文字段缺失、类型错误或隔离未知时，先拒绝推进，不能靠未命中第一条规则绕过检查。
- phase：development或final_check。
- failure_class：passed、assertion_failed、syntax_error、code_runtime_error、environment_error、timeout、permission_violation、model_transport_error、invalid_model_output、final_check_failed、not_reproduced等；兼容读取旧heldout_failed，迁移待B/C确认。
- isolation_ready、user_pause_requested、evidence_matches_current_version。
- repair_budget_available、execution_budget_available、needs_new_repair、next_action_requires_execution_budget。
- output_agent由程序标识模型来源角色；tester等非模型输出为null，不能让模型自报。
- needs_new_repair仅根据当前有效开发证据计算；代码更新但未测试时必须为false，不能因轮数耗尽跳过最后一个候选的测试。

最大修复轮数3可解释为首次尝试加最多2次修复重试；网络重试另设有界配置并计入调用预算。B/C须确认何时占用轮次、无效输出如何计数；没冻结前不批量运行。

超时清理和有效独立验收终态优先于普通暂停。Agent恢复规则只处理development；final_check异常只能结束或交C核查，不能自动回流Agent。陈旧的通过和失败证据都不能终结当前版本，须在预算内重验。定位输出无效暂停查协议；修复输出无效仅能在剩余修复预算内处理。

每个新模型请求、工具执行及重新测试前仍须统一预算闸门。已合法完成的最后一次验收即使刚好耗尽预算，也不能被后续“发起新动作”的预算检查改成失败。达到上限不得额外免费重试。待修文件语法错归syntax_error，测试/依赖配置问题不能靠改业务代码处理。

代码修改后旧验证立即失效；暂停追加约束后须重新核验旧候选。final_check未准备、超时、错误或未知时不能宣布success，验收输出不进入本轮模型修复输入。
