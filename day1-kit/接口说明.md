# Day 1 接口约定

这些是程序之间传递数据的字段约定，不是网站接口，也不是模型服务商的 API。以下内容是供 A、B、C 对齐的模板，不能冒充真实运行记录。B、C 开工时确认后固定字段。

## 1 TaskSpec 谁来修什么

A 维护 configs/task.json；B 读取它，按允许路径、测试命令和轮数执行。
test_command 在运行副本的根目录执行。模型不能自由替换测试命令。
相比手册仅将 pytest 命令明确为 python -m pytest，以使用当前解释器。

## 2 ToolRun 测试工具返回什么

C 与 B 对齐测试工具的结果；测试执行器实际产生 JSON，B 的流程读取。
以下为字段模板，null 表示尚无真实数值：

{
  "call_id": "<本次工具调用唯一编号>",
  "tool": "run_tests",
  "status": "<passed|failed|timeout|error>",
  "exit_code": null,
  "counts": {"passed": null, "failed": null},
  "log_path": "<本次真实日志路径>",
  "duration_ms": null
}

passed：测试实际执行且通过；failed：实际执行但失败；timeout：超时；
error：执行器无法启动等错误。环境导入失败可有非零退出码，但不是测试断言失败，须根据原始输出另作分类。
退出码、计数和耗时必须来自真实执行，解析不到就留 null，不能猜测。
日志必须可打开，路径须指向当前 run_id 下的本次调用。

## 3 Decision 为什么继续或停止

A 确认规则，B 编码执行，C 用测试结果复核。A 不需要每一轮手动填写。

{
  "decision_id": "<本次决定唯一编号>",
  "evidence": "<触发决定的 call_id>",
  "failure_class": "<通过|断言失败|语法错误|环境异常|超时|达到上限>",
  "action": "<结束|重修|暂停|停止>",
  "reason": "<依据证据和剩余轮次说明>",
  "rounds_left": null
}

今天的最低规则：
- 实际通过：结束并记录 success。
- 代码断言或语法失败且未到上限：记录重修，再次调用模型。
- 到达3轮：停止并记录 stopped，不进行第4轮。
- 环境异常、超时：暂停或停止并记录原因，不能记 success。
更完整的重新定位分支安排在 Day 2。

## 4 events.jsonl 发生过什么

B 的程序逐行追加 JSON；E 的台账只引用它，不能人工补造程序事件。
每条建议包含 ts、run_id、event；按事件补 status、call_id、代码版本、轮次等字段。
至少覆盖：任务开始、副本创建、修改前测试、模型定位、模型修复、修改应用、修改后测试、决定、最终结果。
两份提示词在今天可以顺序调用同一家模型，不要求搭建多 Agent 框架。
只有真实发生的调用才记为 model_call；阶段性省略定位员时须明确记录，不能声称已完成两个角色。
